# Перевірка прискорення синхронізації

Тести використовують налаштований Magento runtime та його DB adapter. Вони створюють
шість тимчасових таблиць з унікальними назвами, копіюючи лише структуру довідників.
ResourceConnection у тестовому процесі спрямовує моделі й колекції до цих таблиць.
Робочі записи не копіюються й не змінюються. Таблиці видаляються після тесту;
навіть після втрати DB-сеансу їхні назви не можуть вказати на робочі довідники.

Події моделей реєструються тестовим dispatcher без виконання observers, щоб
перевірка не зачіпала спільні сервіси. HTTP-відповіді задаються fixtures;
реальні запити до Нової пошти не виконуються.

## Запуск

З канонічного checkout із перевіреними Warden mounts:

```bash
warden env exec -T php-fpm vendor/bin/phpunit \
  -c dev/tests/unit/phpunit.xml.dist --no-extensions --do-not-cache-result \
  app/code/Perspective/NovaposhtaCatalog/Test/Unit \
  app/code/Perspective/NovaposhtaShipping/Test/Unit

warden env exec -T php-fpm vendor/bin/phpunit \
  -c app/code/Perspective/NovaposhtaCatalog/Test/Integration/phpunit.xml
```

Без `NOVAPOSHTA_BASELINE_PATH` пропускається лише benchmark. Перевірки реального
запису, rollback, відсутності записів, дублікатів, доступності, історії, подій
і runtime DI виконуються завжди.

Для порівняння потрібна довірена копія модуля **до змін**, доступна в контейнері.
Baseline завантажується під окремим namespace; він не реєструється в Magento DI.
Не підставляйте поточну реалізацію або сторонній неперевірений код як baseline.

```bash
warden env exec -T php-fpm env \
  NOVAPOSHTA_BASELINE_PATH=/tmp/novaposhta-sync-before \
  vendor/bin/phpunit \
  -c app/code/Perspective/NovaposhtaCatalog/Test/Integration/phpunit.xml
```

Benchmark виконує один прогрів і п'ять виміряних повторів для кожної версії.
Fixtures: 20 активних міст, 420 імпортованих записів кожного з двох довідників,
20 000 історичних вулиць, власне пакування, переклад, відсутній в API,
зміна статусу відділення та JSON-розклад. Час зафіксований. У кожній парі запусків
порівнюються SHA-256 усіх рядків шести таблиць, включно з ID й полями safety policy.
Індекс `street.ref` перемикається лише на тимчасовій таблиці.

## Результати 14 жовтня 2026 року

| Медіана п'яти повторів | PHP 8.5.4 до | PHP 8.5.4 після | PHP 8.4.19 до | PHP 8.4.19 після |
|---|---:|---:|---:|---:|
| Тривалість, мс | 362.902 | 290.063 | 401.479 | 298.217 |
| CPU процесу, мс | 178.158 | 183.130 | 210.105 | 196.538 |
| Додаткова пікова PHP-пам'ять, байт | 2 235 128 | 2 235 680 | 2 235 288 | 2 235 840 |
| SQL-запити | 1004 | 1003 | 1004 | 1003 |

Локальна обробка прискорилася приблизно на 20% на PHP 8.5 і 26% на PHP 8.4.
Вміст таблиць збігся в усіх повторах. Різниця CPU на PHP 8.5 не показує виграшу;
пам'ять на цьому невеликому наборі міст практично однакова. Це синтетичний
benchmark без мережевого часу, observers і реальних 429; його результат не є
оцінкою прискорення повного імпорту з НП.

На обох версіях PHP пройшли 250 unit-тестів Catalog/Shipping (1011 assertions)
та 6 інтеграційних тестів із benchmark (94 assertions). DI-компіляція та
перевірки синтаксису також пройшли.

## Локальна міграція й наступний етап

Індекс оголошено в declarative schema та whitelist. На дослідженому локальному
runtime він застосований через Magento DB adapter. Повний `setup:upgrade`
також планував стороннє видалення `tfa_user_config` і `tfa_country_codes`;
ці зміни не виконувалися. Перед звичайним deployment слід перевірити різницю
схеми, виконати необхідну міграцію й оновити DI/config cache.

`warehouse.ref` залишається `LONGTEXT`. Його міграція та пакетний SQL відкладені:
для них потрібні репрезентативні історичні дані та окрема перевірка сумісності.
Зростання частоти послідовних API-запитів після прискорення локальної обробки
слід оцінювати через нові метрики `http_429`, `rate_limits` і `retry_wait`.
